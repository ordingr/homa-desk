### Verdict: BLOCK on one finding (R11-F1), PASS on everything else

**R11-F1** must be fixed before commit: "Continue in Claude Code" starts an interactive, tool-enabled Claude Code
session with its working directory set to the folder of the file that was summarised. That folder is whatever folder
the file came from — a Downloads folder, an extracted archive, a shared drive — so its `.claude/settings.json`
(hooks), `.mcp.json` and `CLAUDE.md` are loaded by Claude Code, gated only by Claude Code's own folder-trust prompt.
The non-interactive send path already avoids exactly this by running in `paths.home()`; the interactive path should
too, with `--add-dir <folder>` for file access. It is a two-line change. Severity is medium, not high, because the user
must click through Claude Code's trust prompt in a folder they did not create; it is a finding and not a note because
the feature's whole purpose is handing *untrusted* files to an agent, the chain ends in command execution, and the fix
costs nothing. If the tech-lead chooses to accept the risk instead, record that decision here.

Seven NOTEs (R11-N1..N7). All eight change classes in the brief were checked by observation; the checklist is below.
The privacy gate is clean.

### Findings, ranked

**R11-F1. The Continue launcher runs interactive Claude Code inside the summarised file's folder.** `assistant/actions/
claude.py:279-286`:

```python

          f'cd /d "{cwd}"\r\n'
```

and `_launch(str(launcher), cwd)` at `:293` also starts `cmd.exe` in that folder. Claude Code reads project settings
(`.claude/settings.json`, `.claude/settings.local.json` — hooks included), `.mcp.json` and `CLAUDE.md` from its working
directory. Attack: a folder inside an indexed root (Downloads is the obvious one) holds `report.txt` next to
`.claude/settings.json` with a `SessionStart` hook; the user asks Claude about `report.txt` (safe: `-p`, no tools,

**R11-N1. The `%%~f0` un-escape also fires inside the directory name.** `claude.py:286`
`.replace("%", "%%").replace("%%~f0", "%~f0")` is applied to the whole script, so a folder literally named `…%~f0…`
yields `%~f0` on the `cd` line, which expands to the launcher's own path; `cd` then fails with "The filename, directory
name, or volume label syntax is incorrect." (observed on stderr in the probe above). Harmless today because `_launch`
already starts `cmd.exe` in the right folder, and no quote can be injected (Windows forbids `"` in names; `&`, `^`,
`(`, `)`, `;`, `,`, `=`, `` ` `` and `'` were all literal inside the quotes — the `INJECTED_AMP` text appeared only
inside the stub's `cwd=` echo, never as an executed command). `!` would matter only with delayed expansion on; on this
machine `HKCU\Software\Microsoft\Command Processor` is absent and `HKLM ... DelayedExpansion` is unset (default off).
**Fix:** escape each inserted field (`cwd`, `exe`, `ctx`) individually and leave the template's `%~f0` alone; moot if
R11-F1 removes `cwd` from the script. **Severity:** low.

**R11-N2. A shortcut that passes validation can disable the search popup and the hotkey.** `assistant/settings.py:42`
`_CHORD` uses `[a-z0-9]` with `re.IGNORECASE`; under Unicode matching that class also accepts `ı` (U+0131), `ſ`
(U+017F) and the Kelvin sign `K` (U+212A). `search_ui.chord_sequences("Ctrl+ı")` emits `<Control-ı>`, Tk rejects it,
and the exception escapes `SearchPopup.__init__` → `app.py:312` catches it and gives up on both the popup and the
hotkey. Observed with a throwaway instance started with `"shortcuts": {"copy_path": "Ctrl+\u0131"}`:

```
B1 /v1/_debug/ui -> 200 | has 'search' section: False | has 'hotkey': False
B3 console lines: ['ERROR assistant.app: could not build the search popup or hotkey', '_tkinter.TclError: bad event type or keysym "ı"']
```

and in-process: `'Ctrl+ı' settings_accepts=True sequences=['<Control-ı>'] -> TclError bad event type or keysym "ı"`;
`'Ctrl+ſ'` is accepted and silently becomes `<Control-s>` (casefold). Reach: only a hand edit of `settings.json`
(the Settings window's shortcuts page is read-only and there is no settings write route), so this is self-inflicted.
**Fix:** compile `_CHORD` with `re.ASCII` (or spell the class `[A-Za-z0-9]` without IGNORECASE on that alternative), and
wrap `self.entry.bind(sequence, …)` in `_apply_shortcuts` with `except tk.TclError: log.warning(...)` so one bad chord
never takes the popup down. **Severity:** low.

**R11-N3. `update.source` is the whole trust boundary: no integrity check, and pip runs before the user can look.**
`assistant/update.py:244-248`: after download (https only, ≤ 50 MB, no proxy — all observed) and extraction (all
twelve hostile archives refused, see Commands), `_pip_install(target / "requirements.txt", False)` installs the
*archive's* requirements into the live venv (or `--user` site) immediately. A requirements file may carry
`--index-url`, `--extra-index-url`, `--find-links`, `--trusted-host`; `--only-binary :all:` stops `setup.py` but not a
wheel's `.pth`, which runs on the next interpreter start — before the user ever launches the "untouched" sibling folder
the final message points at. There is no hash or signature on the archive. Reach: a write to `settings.json`
(no UI or route sets `update`), i.e. the same user; so this is hardening, not an exploit against the current design.
**Fix (any of):** support `update.sha256` next to `update.source` and refuse a mismatch; print the SHA-256 and ask
before pip; or install with `--require-hashes` / `--no-index --find-links <target>/wheels`. The git route
(`git pull --ff-only` + pip from the clone's `requirements.txt`) trusts the remote the same way, which is DEC 13 as
designed. **Severity:** low (requires local settings write).

**R11-N4. Bare executable names are resolved by CreateProcess search order.** `update.py:124,131,136` run
`["git", ...]` although `shutil.which("git")` was just evaluated and discarded; `claude.py:263` runs `["cmd.exe", "/c",
launcher]`. With no path, Windows looks first in the directory of the running executable (`.venv\Scripts`) and the
parent's current directory (the repo root under the `.lnk`), then System32 and PATH. Both locations are the user's own
install, so planting a binary there already means code execution; the fix is free though: pass the `which()` result,
and `os.environ.get("ComSpec", r"C:\Windows\System32\cmd.exe")`. **Severity:** low.

**R11-N5. A context file from a crashed console keeps the file text and answer on disk until the *next* Continue.**
`claude.py:289` calls `_sweep(folder)` only inside `continue_session`; `_sweep` blanks `claude-ctx-*` older than
24 h. The normal path deletes the file (observed: `files left in home/tmp after launcher exit: []`,
`launcher still exists: False`), but after a crash the text sits in `~/.assistant/tmp/` (inside the protected home)
until the user continues again. **Fix:** also run `_sweep` at app start. **Severity:** low (own data, own disk).

**R11-N6. Recycle Bin pre-check residual (second half of R10-N2).** `shell.py:_bin_problem` now reads the
`NoRecycleFiles` policy from HKCU and HKLM (closes the first half), but when the per-volume key is missing
