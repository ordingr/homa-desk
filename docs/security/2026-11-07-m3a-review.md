### Verdict: PASS — zero BLOCK findings. Two FIX-BEFORE-M3B (R7-F1, R7-F2), twelve NOTEs (R7-N1..N12). The plan's two M3a-9 criteria hold by observation: no deny-listed fixture appears in any MCP result with the setting on or off, `GET /v1/search` lists them by name only when `show_protected_by_name` is on and never with content, and every junction escape tried was refused.

The deny-list is applied in four places and they agree: the crawler flags entries at walk time, the executor drops
flagged entries unless the caller passes `show_denied=True`, only `routes_search` and the popup's `_AppFilesMode`
ever pass it, and `mcp.search_files` both passes `show_denied=False` and re-filters rows by name. Path vetting in
`mcp._vet` resolves first (junctions, `..`, trailing dots, case, 8.3 names, `\\?\`), then checks roots, then the
deny-list on both the given and the resolved path, then requires the resolved path to be an index entry — so a
junction to an excluded or deny-listed in-root directory is refused even though it is inside a root, and a directory
swapped for a junction after the crawl is refused at vet time. The query grammar is capped (512 characters, 32
tokens) and the wildcard matcher is segment-based with no quantifiers, so no input I found costs more than linear
time. The restricted unpickler refused every code-bearing pickle shape I crafted. The one finding that matters for
the product is R7-F1: the Assistant's own data folder is not protected from its own index, so a root that covers the
user profile makes the bearer token, the ICS calendar URLs (credentials per SEC-12), the hook backups and the card
state previewable to the MCP client — i.e. to Claude. That is a PRD list gap rather than a code bug, but it is the
exact risk class SEC-3 exists for, so fix it in the first M3a follow-up, before a real root is configured.

#### FIX-BEFORE-M3B

**R7-F1. The Assistant's own home folder is indexed and previewable: token, `settings.json` (ICS URLs), hook
backups, `state.json`, logs.** `assistant/security/denylist.py:18-56` (no pattern covers `.assistant/`, `.claude/
settings.json` or `.claude.json`), `assistant/index/excludes.py:28-78` (`DEFAULT_EXCLUDES` has no rule for the home),
`assistant/server/mcp.py:169-188` (`_vet` has no "own data" refusal). Observed live, instance with roots
`[<root>, <home>]` (the `<home>` is the instance's `ASSISTANT_HOME`; a real user would get the same by indexing
`C:\Users\<user>` or the whole drive, which is the natural root choice), `show_protected_by_name` either way:

```
read_text_preview(<home>\token)          -> 200 OK  body line 1 = the 43-character bearer token (token-in-body=True)
read_text_preview(<home>\settings.json)  -> 200 OK  body contains the planted ICS URL https://calendar.example/private-SECRET-URL-9f1/basic.ics
read_text_preview(<home>\logs\app.log)   -> 200 OK  (home path, port, token-created line)
read_text_preview(<home>\assistant.pid)  -> 200 OK
read_text_preview(<home>\state.json)     -> refused at first (not indexed yet); after one POST /v1/cards the watcher
                                            added it to the delta and the preview returned it within 2 s, including the
                                            card detail  "LEAKDETAIL curl -H 'Authorization: Bearer abc'"
read_text_preview(<home>\index\files.idx)-> refused (binary sniff)   get_file_info(<home>\token) -> metadata returned
in-process, crawler on a copy of a home: <home>\hooks-backup\1.json -> RETURNED  {"hooks": {"Authorization": "Bearer AAAA…
GET /v1/search?q=state.json              -> ['state.json'] listed (setting off)
```

Attacker model: none needed — the MCP client is the user's own Claude Code/Desktop session, which already holds the
bearer token (so the token line is not a new disclosure). What *is* new: the ICS URLs (SEC-12 treats them as
credentials and keeps them out of logs, health and `--doctor`), the user's entire pre-install Claude Code settings in
`hooks-backup/` (Review 3 N5: may hold their own `env` secrets), hook payload summaries in `state.json` (commands the
user ran, Review 3 N11), and the notes index `notes.json.gz` once M3b adds a gzip-aware preview. All of it would be
handed to the model on a "what is in my settings" question, which is the SEC-3 failure mode. Not a BLOCK because the
default roots are empty and the plan's M3a-9 criteria (deny-listed fixtures, junction escape) hold; it must land
before the user configures a real root. Fix (three layers, any one suffices for the token/ICS case, all three for
defence in depth): (a) `index/manager.py:_apply_config()` appends an absolute exclude rule for `paths.home()` (and
`**/.assistant/`) to the compiled `Excludes`, so the folder is never indexed — and `routes_search`/the popup never see
it; (b) `mcp._vet()` refuses any resolved path under `os.path.realpath(paths.home())` with its own reason ("the
Assistant's own data folder"), independent of the index; (c) `denylist.DIR_PATTERNS` gains `.assistant`, and
`TAIL_PATTERNS` gains `.claude/settings.json` and `.claude.json` (both carry the bearer token / MCP headers). Add
`tests/test_mcp_files.py` cases: a root that contains the instance home → `read_text_preview(<home>/token)` and
`(<home>/settings.json)` refused, `search_files("settings.json")` returns no `<home>` row.

**R7-F2. Full-scan queries cost 2.5–7 s each on a 2,000,000-entry index and the HTTP dense-query cap is defeated by
`offset`.** `assistant/index/search.py:281-291` (`_candidates` falls back to `range(store.entry_count)` when the
name term has no literal and no extension filter), `:197-257` (per-candidate Python loop), `assistant/server/
routes_search.py:92-93` (`_CappedStore(store, max(DENSE_CAP, offset + limit))` — the cap is only applied for
`sort != best`, and `offset` lifts it), `:51-61` (`_int_param` has no upper bound). Observed in-process on the
synthetic 2M store (`conftest.build_synthetic_store`, 115 MB private):

```
q='rep'                       total=195177  425 ms       q='report' limit=1e9        rows=10000   645 ms  (search.run clamps to 10,000)
q=''                          total=2020001 2462 ms      q='report' offset=1e15      rows=0       588 ms
q='*'  / q='?'                total=2020001 5120 / 5967 ms
q='e'                         total=1755767 4978 ms      q='e' sort=name             3818 ms
q='!report'                   total=1824824 5911 ms      q='path:d000'  total=10100  3042 ms
_CappedStore(cap=max(DENSE_CAP, 1e15+50)) q='e' sort=name -> total=1755767 truncated=False  6792 ms
```

Each such request holds one Starlette threadpool thread and the GIL for its duration; the popup itself issues a
one-letter query on the first keystroke, and `/v1/search` is reachable by any token holder (local, so availability
only — NOTE on this review's severity scale). It is FIX-BEFORE-M3B because M3b's full page will send a request per
keystroke and `tests/perf/test_query_latency.py` samples 2–6 character queries, which hides the one-character and
empty-term cases (`rep` → 425 ms vs `e` → 5 s). Live on the 680-entry fixture the same queries took 15–28 ms and 20
threads hammering `q=e&limit=10000` for 3 s (406 requests, max 225 ms) left `/v1/health` at 200 in 149 ms, so the
small-index behaviour is fine; the cost is linear in candidates. Fix: cap `offset` at the route and in
`search_files` (e.g. ≤ 100,000; `_int_param` already has the shape), apply the candidate cap to `sort=best` as well
when `_is_plain_single_term` (ranking the first `DENSE_CAP` hits by tier is an acceptable approximation and the
response already carries `truncated`), and give `search.run` a wall-clock budget (check every 50,000 candidates,
stop with `truncated=True`) so no request exceeds, say, 1 s regardless of query shape.

#### NOTE (hardening, tracked)

**R7-N1. `IndexStore.load` validates lengths and `parent` bounds but not element types or root coverage.**
`assistant/index/store.py:286-312`. Observed: a well-formed file with `names` re-encoded as `bytes` loaded (entries=2;
every query would then raise `TypeError` in `str.find`); `dirs=[12345]` loaded, then `store.path(1)` →
`AttributeError: 'int' object has no attribute 'endswith'`; `roots=[]` with a `parent == -1` entry loaded, then
`store.path(0)` → `KeyError: 0`. Writing `~/.assistant/index/files.idx` needs the user's own access, so this is
robustness, not a boundary; `manager._load_persisted()` catches load-time exceptions but these surface at query time
as 500s/tool errors until the next walk replaces the store. Fix: in `load()`, require `isinstance(names, str)`,
`isinstance(cf, str)`, `all(isinstance(d, str) for d in dirs)`, every `parent >= -1`, and every index with `parent == -1`
present in `roots`. The code-execution surface is closed: `os.system` via `__reduce__`, `GLOBAL`, `STACK_GLOBAL`,
`NEWOBJ` (a `Path`), all → `UnpicklingError: index files hold plain data only`; `EXT1` → `ValueError: unregistered
extension code`; a declared 2^63-byte `BINBYTES8` → `OverflowError`; a declared 2 GB `BINUNICODE8` → `pickle data was
truncated`; wrong magic / non-dict → `ValueError`; `save()` into a missing directory left no `.part` behind.

**R7-N2. Check-then-open window in `read_text_preview`, and index membership is advisory.** `mcp.py:181-188` resolve
and vet, `:220` open — a same-user process that swaps a path component for a junction *between* those two calls would
be followed by `open()`. The pre-vet swap is handled (observed: `docs\swap` replaced by a junction to outside →
"outside the indexed roots"; to the in-root `secrets` dir → "protected file"; to `node_modules\pkg` → "not in the
index"). The remaining window is microseconds and the attacker already runs as the user, so threat-model only.
Hardening if wanted: open first with `FILE_FLAG_OPEN_REPARSE_POINT` semantics or compare
`win32file.GetFinalPathNameByHandle(fh)` with `resolved` before reading; use `os.lstat` in `_metadata` for the
placeholder check. Related: `_indexed()` (`:156-166`) ignores delta removals — a path deleted after the crawl and
recreated is still "indexed" (observed: delta-removed `docs\readme.txt` still vetted OK). Harmless because roots and
deny-list are re-checked on the real path, but the docstring's "so root, exclude and junction rules all hold" is only
true for the crawl-time tree.

**R7-N3. Deny-list coverage: the PRD list is implemented exactly; common secret stores outside it are not covered.**
`denylist.py:18-56`. Every PRD default pattern matched its canonical example (`.env*`, `*.pem`, `*.key`, `*.pfx`,
`*.p12`, `*.ppk`, `*.kdbx`, `id_rsa*`, `id_ed25519*`, `.git-credentials`, `.netrc`, `.npmrc`, `.pypirc`, kubeconfig
both spellings, `.aws/credentials`, `.docker/config.json`, `.kube/config`, Chrome/Edge/Firefox profile dirs, KeePass,
Bitwarden, 1Password …), case-insensitively and with either separator. Not matched: `id_ecdsa`, `id_dsa`, `.ssh/`
as a directory (`authorized_keys`, `known_hosts`), `.gnupg/`, `*.asc`, `*.p8`, `*.jks`/`*.keystore`, `.pgpass`,
`.htpasswd`, `.config/gh/hosts.yml` (GitHub CLI token), `.azure/*token_cache*`, `.aws/config`, and the R7-F1 set. The
list is user-editable, so this is a defaults question for product; recommend adding `id_ecdsa*`, `id_dsa*`,
`*.p8`, `*.jks`, `*.keystore`, `.pgpass`, `.htpasswd`, `*.asc` to `NAME_PATTERNS`, `.ssh`, `.gnupg`, `.azure`,
`.config/gh` to `DIR_PATTERNS`. 8.3 short names: `ENV~1` is not matched by name (observed `False`), but `_vet` also

volume (`GetShortPathNameW` returned the long names; `fsutil 8dot3name query` needs admin), so this is reasoned from

ENCRYPTED, EC, DSA and PGP block headers; it does not match a lower-cased or space-padded header, PuTTY `.ppk`
content (name-denied anyway) or UTF-16 text (refused earlier as binary, observed).

**R7-N4. `search_files` with an out-of-range `filters.modified_after` raises an unexpected exception.** `mcp.py:
266-270` catches `ValueError` only; `datetime.fromisoformat("0001-01-01").timestamp()` (also `9999-12-31`,
`1969-12-31`) raises `OSError: [Errno 22]` on Windows. Observed live: the caller gets the generic `Error executing
tool search_files`, and `app.log` gets an `ERROR mcp.server.mcpserver.server: Tool 'search_files' raised an unexpected

traceback. Fix: catch `(ValueError, OverflowError, OSError)` and clamp years to 1970–2100 as `ics._parse_time` does;
`search._resolve_date()` has the same exposure through `_fmt_day`.

**R7-N5. The notes index persists passages of deny-listed notes and filters only at query time.**
`notes_bm25.py:328-359` indexes every `.md` the walk yields; `_denied()` is applied in `search()` (`:465`). Observed:
vault with `id_rsa.md` and `AppData\Roaming\KeePass\kp.md` → both in `_files`, neither in results for `alpha`, but
`notes.json.gz` holds "secret passage" and "keepass note" in clear (gzip). The file lives in the user-only home, so
exposure is nil today; it becomes R7-F1 material if the home is indexed. Fix: skip denied paths in `_sync()` and count
them like placeholders. Confirmed sound: the OFFLINE note was never opened (audit hook), the junction out of the
vault was not followed, a 2 MB + 6 byte note was skipped as large, dot-directories are skipped, and
`ASSISTANT_NOTES_DIR` overrides the setting (the environment is the user's; recorded).

**R7-N6. `GET /v1/search` has no route-level `limit`/`offset` cap.** `routes_search.py:51-61`. `search.run` clamps
`limit` to 10,000 (observed: `limit=999999999` → 200 with all 5 rows; `q=e&limit=10000` → 641 rows on the fixture),
so the worst case is a ~3 MB JSON body per request on a large index; `offset=1e15` → 200, empty page. Cap at the
route (`limit ≤ 1000`, `offset ≤ 100000`) and it also closes the R7-F2 `_CappedStore` bypass. `limit=1e9` → 422
`limit must be an integer.`, `limit=-1` → 422, `sort`/`chips`/`modified` garbage → 422 naming the field, a 100 KB `q`
→ 400 from uvicorn (URL too long), `q=%00` → 200 empty (the NUL term matches nothing by design).

**R7-N8. One asyncio `_ProactorReadPipeTransport._loop_reading()` ERROR traceback in `app.log`** after the probe's
