#### FIX-BEFORE-M3

**R5-F1. A join URL with userinfo or a dotted "port" passes the Zoom/Teams/Meet/Webex allow-list, so a meeting card's
click opens an attacker host under a "Zoom" label.** `assistant/calendar/meetings.py:28-31` (`_JOIN_RE`), `:58-68`
(`find_join_url`). The regex anchors the host with `(?![A-Za-z0-9.-])` and then consumes `[^\s<>"'...]*`, so `@` and `:`
are accepted after the allow-listed host and the URL continues into the attacker's authority. Observed in-process:

```
find_join_url('https://zoom.us@evil.example/phish')                  -> 'https://zoom.us@evil.example/phish'
find_join_url('https://teams.microsoft.com@evil.example/l/meetup')   -> 'https://teams.microsoft.com@evil.example/l/meetup'
find_join_url('https://zoom.us:443.evil.example/x')                  -> 'https://zoom.us:443.evil.example/x'
find_join_url('https://zoom.us.evil.example/')                       -> None   (correct)
find_join_url('https://evil.example/?u=https://zoom.us/j/1')         -> 'https://zoom.us/j/1'   (correct)
```

Live: an ICS event with `LOCATION:Room 1 https://zoom.us@evil.example/phish` produced, at T-5 min, the card
`title='Budget, review EVIL starts in 5 minutes' detail='22:48–23:18 · Room 1 https://zoom.us@evil.example/phish · Zoom'
url='https://zoom.us@evil.example/phish'`; `App._open_url` accepts it (starts with `https://`) and the browser navigates to
`evil.example` (Chromium and Edge drop the userinfo from the address bar but honour the host). Attacker model: anyone who
can get an event into the user's calendar — a meeting invite to the user's address, which Outlook and Google add as
tentative — so this is reachable from outside the machine, unlike every other finding in this review. The user still has
to click, and the card shows the raw URL in the detail, which is why this is not a BLOCK; it is the one finding that
widens the attack surface beyond "already runs as the user". Fix: after the regex match, `urlsplit(url)` and require
`username is None and password is None`, `hostname` equal to or ending with `.` + an allow-listed domain, and `port in
(None, 80, 443)`; otherwise drop the candidate and keep scanning. Add the four strings above to `tests/test_meetings.py`.

**R5-F2. One malformed event aborts the whole feed, silencing every meeting from that calendar.** `assistant/calendar/
ics.py:409-415` (`_parse_duration` builds a `timedelta` from an unbounded integer), `:395-406` (`_parse_time` →
`strptime` accepts year 0001 and 9999 for `VALUE=DATE`), `:436-451` (`_localize(...).astimezone()` on those values), and
nothing in `_parse_feed()` (`:106-133`) isolates one `VEVENT` from the next. Observed in-process:

```
DURATION:P999...9D (400 digits)                 -> OverflowError: Python int too large to convert to C int  (escapes parse_ics)
DTSTART;VALUE=DATE:00010101 / DTEND 99991231    -> OSError: [Errno 22] Invalid argument                       (escapes parse_ics)
```

`MeetingScheduler._poll_one()` (`meetings.py:198-213`) catches it, records `last_error = "OverflowError"` for the whole
source, drops the source's events, and after one hour raises the "Calendar not updating" card. One hostile or merely
broken invite therefore removes every meeting card from that calendar for as long as the invite exists. Same attacker
model as R5-F1 (an invite), availability only. Fix: wrap the per-event `_event_info(props)` call in `_parse_feed()` in
`try/except (ValueError, OverflowError, OSError)` and skip that event with one `log.debug`; clamp `_parse_duration` to,
say, 366 days and refuse `DTSTART`/`DTEND` years outside 1970–2100 in `_parse_time`. Add both feeds to `tests/test_ics.py`.
Everything else thrown at the parser held: traversal-shaped `TZID`s (`..\..\Windows\win.ini`, `../../etc/passwd`,
`C:\...`) resolve to nothing and fall back to UTC (`ZoneInfo` rejects them, no file is opened); `COUNT=` 5,000 digits,
`COUNT=1e9`, `INTERVAL=` 5,000 digits, `INTERVAL=-5`, `UNTIL=9999...`, nested `BEGIN`, an unterminated feed, a 200,000-entry
`EXDATE` (2.8 s), 3,000 distinct bogus `TZID`s (1.1 s), an 8.9 MB feed with 30,000 events (2.1 s) all returned normally.

**R5-F3. `token.regenerate()` fails with `PermissionError` whenever any reader has the token file open, and the app now
reads the token file on every request.** `assistant/security/token.py:38` (`os.replace(tmp, final)` with no retry),
`assistant/app.py:218-223` (`_current_token()` calls `token_store.read()` per request). On Windows a file opened by
Python's `open()` is shareable for read and write but not for delete, so `MoveFileEx(REPLACE_EXISTING)` fails while the
read is in flight. Observed in-process with four threads looping `token.read()` (695 reads) while regenerating 60 times:

```
regenerate failures=39/60  PermissionError: [WinError 5] Access is denied: '<home>\token.tmp' -> '<home>\token'
reader failures=9/695      PermissionError   (the app's _current_token() swallows these and keeps the cached token)
token.tmp left behind: False   token ACL afterwards: <user>:(F) single ACE
```

In the app the readers are the hook receiver, MCP calls, the CLI and the Settings window, each holding the file for
microseconds, so an ordinary user-initiated Regenerate collides rarely — but when it does the user sees "could not
regenerate the token (PermissionError)" and the old token stays valid, and a same-user process that deliberately keeps
`token` open blocks revocation indefinitely (it already runs as the user, so NOTE-grade as a security issue; the
robustness bug is what makes this FIX-BEFORE-M3 — AC-MC-9's one feature is unreliable by construction). Fix: in
`_write_new()`, retry `os.replace` with the same backoff `settings._replace()` already uses (10 attempts, 10 ms → 200 ms);
in `App._current_token()`, cache the token with the file's `st_mtime_ns` and re-read only when the stamp changes (one
`stat()` per request instead of an open/read), which also removes the per-request read as a collision source. Regeneration
otherwise behaves: the old token is 401 on the next request (qa's test and the per-request read guarantee it), the new
file carries the single-ACE DACL, and `token.tmp` never survives.

**R5-F4. `hooks remove` restores a backup that contains Assistant's own hook entries, so after a user edit followed by
Regenerate (or any reinstall) the hooks survive removal and keep posting a revoked token.** `assistant/hooks_installer.py:
140-153` (a new backup of the *current* file is taken whenever its hash differs from the recorded one — after the user
has edited the file, that current content includes our entries), `:168-180` (`remove()` restores that backup verbatim
when the file still hashes to what we last wrote). Observed in-process against a scratch profile:

```
install -> user adds "permissions" to settings.json -> regenerate() [hooks='updated']:
  backups=2; newest backup contains our http hook: True; contains the now-revoked token: True
remove() -> 'restored <profile>\.claude\settings.json from <backup>'
after remove(): installed()='yes (all 8 events)'; our entries present=True; revoked token in file=True
```

Consequence: `uninstall.ps1:35` runs `hooks remove`, reports success, and Claude Code goes on sending every hook event
with `Authorization: Bearer <revoked>` to the port — 401 per tool call in `app.log` while the app runs, and the full hook
payload (cwd, tool input, last message) to any later squatter of the port once it does not (Review 3 F3 model). The
revoked token is also preserved in `hooks-backup/` (fine: revoked). Fix: in `remove()`, after reading the backup, run
`_strip_ours()` on it before writing; in `install()`, strip ours from `raw` before writing a backup, or only ever keep the
first backup as the restore source. This is M1 installer code, but the M2 Regenerate button is what makes the
"reinstall after a user edit" path routine. The foreign-file paths hold: `{not json` → `failed: Claude Code settings
unreadable`, file untouched; `hooks.Stop` not a list → same; no file → `not installed`, no file created.

**R5-F5. The Outlook COM source is on by default and the whole `calendars` section snaps back to defaults on any invalid
key, so classic Outlook is automated without the user enabling it.** `assistant/settings.py:27` (`"outlook": True`),
`assistant/app.py:239-242` (added whenever `OutlookSource.available()` finds the registry key), `assistant/settings.py:
78-83` (`_merged()` replaces the entire `calendars` object with `DEFAULTS["calendars"]` when `_check_calendars` fails),
`overlay/settings_ui.py:331-333` (checkbox pre-ticked). Observed in-process via the 5-s watcher:

```
external edit {"port":80,"calendars":{"ics_urls":[...10000...],"poll_minutes":0}, ...}
  -> WARNING invalid calendars in settings; using default
  -> ics_urls count 0, outlook True, poll_minutes 5   (all three ICS URLs dropped, Outlook switched on, on_change('calendars') fired)
external edit {"calendars":{"ics_urls":["http://a.example/SECRET"],"outlook":"maybe"}}
  -> same: ics_urls 0, outlook True
```

`--doctor` on this laptop reports `Outlook COM available`, so a default start here would `Dispatch("Outlook.Application")`
every five minutes. `outlook.py:59-91` is read-only (`GetDefaultFolder`, `Items.Restrict` with a `strftime`-built filter,
property reads; no `Save`/`Send`/`Delete`), but `Dispatch` starts `OUTLOOK.EXE` headless when it is not running, and
reading `item.Body` (`:88`) is a property the Outlook Object Model Guard can prompt on under corporate policy — a dialog
every five minutes on exactly the laptop class the product targets. PRD AC-MT-2 says the source "can be enabled", which
reads as opt-in, and SEC-10's only sanctioned unattended traffic is ICS polling. **Not run here**: I did not Dispatch
Outlook on this machine (it would start the user's mail client), so the guard-prompt and start-up cost are inferred from
the API, not observed. Fix: `"outlook": False` in `DEFAULTS` and the first-run checkbox; validate `calendars` per key in
`_merged()` (fall back one key at a time, keep valid `ics_urls`); cap `ics_urls` (see R5-N7).

#### NOTE (hardening, tracked)

**R5-N1. `mcp.log` line injection through the tool name and argument keys.** `server/mcp.py:61-63` writes
`str(params.get("name"))[:64]` and `str(k)[:32]` raw. Observed live: `tools/call` with name
`send_card\n2026-11-06T00:00:00 tools/call tool=INJECTED args=[] result_bytes=0 ok` and an argument key `detail\nINJECTED=str[1]`
produced two forged-looking lines in `mcp.log` (returned verbatim by `GET /v1/mcp/log`). Token holder only, and the
log is shape-only, so this is cosmetic trust in a log a human may read. Fix: pass name and keys through
`model.strip_control()` and replace `\n`/`\r` (the `mcp` library already logs the same name with `%r`, one line, at INFO
in `app.log` — observed).

**R5-N2. `GET /mcp` opens a standalone SSE stream that never ends, in stateless mode.** Observed live: `GET /mcp` with
`Accept: text/event-stream` → 200, `cache-control: no-cache`, chunked body with no end (3 s timeout hit); 50 such streams
opened in 0.7 s and were held concurrently while `/v1/health` still answered 200. Each holds a connection, an anyio task and
a transport. Stateless mode has nothing to deliver on that stream. A token holder can exhaust handles (local DoS of the
API; the overlay keeps working). Fix: in `_McpApp.__call__` or `_ExactMount`, answer anything but `POST` with 405
(`DELETE` already gets 405 from the library: "Session termination not supported"). `PUT`/`OPTIONS` → 405 observed.

**R5-N3. ICS fetch follows redirects to any `http`, `https` or `ftp` target.** `ics.py:76-79` uses the default
`urllib.request.urlopen` opener. Observed with a loopback sink: a 302 to another loopback port was followed (second port
received `GET /landed`); a 302 to `ftp://127.0.0.1:1/x` was *attempted* (2 s, `ConnectionRefusedError` — urllib's FTP
handler is in the default opener); a 302 to `file:///...` was refused (`HTTP 302`, urllib allows only http/https/ftp);
a self-redirect loop stopped after urllib's 10 hops. The feed operator already controls the content, so the value is a
blind SSRF from the laptop (one GET every poll to an address of their choosing, response discarded). The default opener
also honours the system HTTP proxy (environment, then WinINET registry) — for the ICS fetch that is **intended** (the
feed is the one sanctioned outbound call, SEC-10, and the corporate proxy is the only way out), unlike `send.py`, which
must never proxy (Review 3 B1). Fix: build one module-level opener for ICS with `ProxyHandler()` (default, so the system
proxy still applies) plus a `HTTPRedirectHandler` subclass whose `redirect_request()` returns `None` unless the new URL's
scheme is `http`/`https`, and cap hops at 3; record the proxy difference next to the opener so a future B1-style sweep
does not "fix" it. The 8 MiB cap holds (`feed too large` on 8 MiB + 1 observed), gzip is not decoded (no
`Accept-Encoding`, a `Content-Encoding: gzip` body is read raw → "not an iCalendar feed"), and every error text stayed
free of the path and query: `HTTP 404`, `HTTP 500`, `HTTP 302`, `feed too large`, `gaierror: [Errno 11001] getaddrinfo
failed`, `ConnectionRefusedError: [WinError 10061] ...`.

**R5-N4. `_WARNED_TZIDS` grows without bound and each new TZID writes feed content to `app.log`.** `ics.py:232,255-257`.
Observed: 3,000 distinct `TZID=Bogus/ZoneN` → set grew 2 → 3,002, one WARNING line each (`calendar feed uses time zone
'Bogus/Zone17' which cannot be resolved`). Per process, deduplicated across polls, bounded by log rotation; still the same
shape as Review 3 N2. Fix: cap at 50 entries with one "further unknown time zones not logged" line (the `_logged_unknown`
pattern in `model.py:106-114`).

**R5-N5. Bearer masking covers `tool_input` only.** `cards/claude_sessions.py:40-45,60-70` (`_mask` applied in
`_tool_summary`), but `_notification()` (`:164` `message`), `_stop()` (`:178-179` `last_assistant_message`) and
`_stop_failure()` (`:195-199` `error*`) go through `_text()` alone. Observed in-process with a 43-character token:
`cc-wait-s1` (PermissionRequest) detail `curl -H 'Authorization: *** http://x` (masked); `cc-wait-s2` (Notification
message), `cc-done-s3` (Stop snippet) and `cc-wait-s4` (StopFailure error) all showed `Bearer AAAA…` in full. Same trust
level as Review 3 N11 (shown on screen and in `state.json`, never logged). Fix: `_text(_mask(...))` in the three places.

**R5-N6. The token's additional homes after M2: the clipboard, the shell history and `~/.claude.json`.** `settings_ui.py:
457-467` puts the real token on the clipboard with `claude mcp add ... --header "Authorization: Bearer <token>"`; Tk
leaves it there after the window closes, Windows Clipboard History (Win+V) keeps it if enabled, and cloud clipboard sync
would send it off the machine (SEC-10 — user-initiated, off by default in Windows). Pasting the command stores it in the
PowerShell/PSReadLine history file in plain text, and `claude mcp add` writes it to `~/.claude.json`. Review 3 N5's README
duty is done for `~/.claude/settings.json` and `hooks-backup/` (README lines 87, 212, 224) — extend the same paragraph to
these three; consider clearing the clipboard after 60 s if it still holds our text. On screen the token is `<token hidden>`
(observed in the code path `mcp_command_text(masked=True)`), Regenerate needs two clicks within 4 s, and
`debug_state()` exposes only the masked command.

**R5-N7. No cap on the number or length of `calendars.ics_urls`, and sources poll serially under one gate.**
`settings.py:47-49` accepts any list of strings; `meetings.py:181-192` polls sources one after another with a 15 s
socket timeout each and skips the poll if the previous one is still running. A long list or one slow feed (a server
trickling bytes resets the per-operation timeout) stalls meeting cards from every calendar. Only the user writes
`settings.json`, so availability only. Fix: cap at 20 URLs of ≤ 2,048 characters in `_check_calendars`; give each source
its own deadline (thread with join timeout, or `socket.setdefaulttimeout` plus a wall-clock cap on the read loop).

**R5-N8. Pydantic validation errors echo the rejected value back to the caller.** Observed: `send_card(title=12345)` →
`isError` text `... Input should be a valid string [type=string_type, input_value=12345 ...`. The caller sent it, so no
disclosure; `app.log` gets only `Tool 'send_card' rejected arguments: ['title']` (field names, library behaviour,
observed). Recording so nobody later routes `isError` text into a log. Our own `ToolError`s name the field only
(`kind: kind must be one of ...`, `id: No card with that id.`, `title: title must be at most 120 characters.` — observed).

**R5-N9. Settings reload does not re-apply the per-file ACL and the live default layout relies on folder inheritance.**
`settings.py:167-194` (`_check_external` reads only). `save()` applies the single-ACE DACL once `ics_urls` is non-empty
(R2-11, observed `<user>:(F)` after `Settings.set("calendars", {...ics_urls...})`, no `settings.json.tmp` left behind), and
a hand edit of that file keeps the DACL (observed `(F)` after the external write). A file written by hand *before* the
first save — the live probe's case — carries the inherited `(I)(F)` from the home folder, which `secure_home()` makes
user-only, so the principals are the same unless `secure_home()` declined (foreign files present). Fix if desired:
re-apply in `_check_external` when `ics_urls` is non-empty.

**R5-N10. R4-1 is narrowed as designed, not closed.** `send.py:44-58`: with no `assistant.pid`, a listener whose image is
`python.exe`/`pythonw.exe` still receives the token. Observed: python `http.server` squatter, no pid file → `send` exit 0

returned the same text as a JSON-RPC error (`code -32000`); pid file naming another pid → refused, nothing sent. The

Accepted; threat-model note.

`routes_health.py:31` tails the file with `str.splitlines()`, which honours both. Observed live: two `tools/call` entries
with a key `k\r\x1b[31m\u2028<marker>` → `mcp.log` holds 4 physical `\n` lines and 2 U+2028 bytes; `_tail()` (the
`/v1/mcp/log` reader) returns **6** lines, the two trailing halves standing alone. The 64-character tool-name budget is
enough for a plausible forged `<stamp> tools/call tool=x args=[] ok`. Token holder only, log is shape-only — same grade
as R5-N1. Fix: in `_one_line`, drop characters whose `unicodedata.category` is `Zl`/`Zp` (or keep only
`ch.isprintable()` plus space), and/or make `_tail` split on `\n` only. `\x85`, `\x0b`, `\x0c` are already stripped (Cc).

**R6-3. The `FILE_SHARE_DELETE` read does not do what its docstring says; the retry loop is the fix.** `token.py:45-46`
("so an open read never blocks the replace in regenerate()"). Observed: `os.replace` over a target held open **with**
`FILE_SHARE_DELETE` → `PermissionError winerror=5` (and after the full budget: `PermissionError after 5.17s`);
`os.unlink` of the same held target succeeds (delete-pending) — Python's `MoveFileExW(REPLACE_EXISTING)` does not use
POSIX rename semantics, so any open handle blocks the superseding rename. Controlled comparison, 60 regenerations under 4
spinning readers:

```
win32 FILE_SHARE_DELETE readers   failures=0  os.replace attempts=97  (retries=37)   elapsed=0.94s  reader errors={}
plain open() readers              failures=0  os.replace attempts=199 (retries=139)  elapsed=9.10s  reader errors={'PermissionError': 33}
REPLACE_BUDGET_S=0, win32 readers failures=18 (retries=0)
REPLACE_BUDGET_S=0, plain readers failures=42 (retries=0)
```

So the share-delete path earns its keep only as a narrower hold window (fewer retries, no reader-side
`PermissionError`), and the pywin32-less fallback is equally correct. Fix: reword the docstring so nobody later removes
`_replace()` believing the share flag suffices; the code can stay. No security impact.

**R6-4. `Regenerate token` runs on the Tk thread and can now stall the Settings window for 5 s.** `settings_ui.py:499-502`
calls `token_mod.regenerate()` inline (the hooks installer at `:424` uses a worker thread); with the file held elsewhere the
window freezes for `REPLACE_BUDGET_S` and then shows `could not regenerate the token (PermissionError)`. Robustness, not
security: the old token stays valid and `token.tmp` is removed. Fix: run it on the same worker-thread pattern, or shorten
the budget to about 2 s (the observed collision needs at most a few 200 ms retries).

**R6-5. The long-token mask now blanks ordinary 40+ character identifiers in Stop and Notification text.**
`claude_sessions.py:33` (`_LONG_TOKEN = [A-Za-z0-9_-]{40,}`) applied to `last_assistant_message` since M2-9: a 64-hex commit
SHA rendered as `commit *** done` (observed), and `_AUTH_HEADER` swallows a trailing `;`. Accepted trade-off (qa adjusted
`test_hooks_statemachine.py:201-207` for it); recorded so the behaviour is traceable, not for action.
