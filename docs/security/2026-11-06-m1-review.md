### Verdict: BLOCK — one BLOCK finding (B1), four FIX-BEFORE-M2, twelve NOTEs.

The HTTP surface, hook receiver, file drop, token/ACL handling, `/v1/shutdown`, `/v1/_debug/ui` gating and
the hooks installer all hold under the attacks below. The block is in `assistant/send.py` (M1-5): the CLI
sender uses `urllib.request.urlopen()` with its default opener, which routes the loopback request — bearer
token and card body included — through any HTTP proxy named by `HTTP_PROXY`/`http_proxy` when `NO_PROXY`
does not cover `127.0.0.1`. That breaks SEC-10 ("nothing leaves the PC") and SEC-2 on exactly the machine
class the product targets. The fix is a few lines; re-verification is one command (listed under B1).
Everything else may merge once B1 is fixed; the FIX-BEFORE-M2 items are robustness and blast-radius issues
in the same files and should land in the M1 follow-up, F1 first (it is a product-breaking bug reachable by a
legitimate reminder).

### Findings, ranked

#### BLOCK

**B1. `send` and `shutdown` send the bearer token and card body to an environment-configured HTTP proxy.**
`assistant/send.py:35` (`urllib.request.urlopen(request, timeout=timeout)`), reached from `run_send()`
(`:64`), `run_shutdown()` (`:83`) and therefore from `uninstall.ps1:19`. The default urllib opener installs
`ProxyHandler()` built from `getproxies()`, and on Windows `proxy_bypass()` consults the `no_proxy` variable
when environment proxies are set and the WinINET registry (`ProxyEnable`/`ProxyServer`/`ProxyOverride`)
otherwise; `127.0.0.1` is not bypassed by default in either path (CPython's `<local>` rule matches only
hostnames without a dot). Observed with a scratch `ASSISTANT_HOME`, nothing listening on the configured
port, and a local sink standing in for the proxy:

```
HTTP_PROXY=http://127.0.0.1:<sink>  (NO_PROXY unset)
python -m assistant send --title PROXYLEAK      -> exit 0, prints "px" (the sink's answer)
sink received: POST http://127.0.0.1:17171/v1/cards HTTP/1.1   Host: 127.0.0.1:17171
               Authorization present: True   body: {"title": "PROXYLEAK", "kind": "custom"}
python -m assistant shutdown                     -> sink received POST http://127.0.0.1:17171/v1/shutdown, Authorization present
NO_PROXY=127.0.0.1,localhost                     -> sink received nothing; send reports "Assistant is not running"
```

Attack/impact: no attacker action is needed — a corporate laptop with `HTTP_PROXY` set for pip/npm/git (the
install target per DEC/PRD) sends the token and every `send` payload in clear text to the proxy, and the
`uninstall.ps1` shutdown step does the same. The token only unlocks the loopback API on that machine, so the
credential value to the proxy operator is low; the violation of the hard privacy constraint is the finding.
This machine has `ProxyEnable=0`, no `ProxyServer`, and `getproxies()` returns `{}`, so the registry path is
**unverified** (testing it means writing the user's registry, which this role does not do); CPython's
`proxy_bypass_registry` source makes the outcome the same whenever a static proxy is enabled and
`ProxyOverride` does not list `127.0.0.1`. PAC/auto-config setups are not read by urllib, so they are safe.
Fix (all in `send.py`): build one opener with `urllib.request.ProxyHandler({})` (empty mapping = always
direct) and a redirect handler whose `redirect_request()` returns `None` (see N1), and use
`_opener.open(request, timeout=...)` instead of `urlopen`. Add a qa test that runs `send` with `HTTP_PROXY`
pointing at a local sink and asserts the sink receives nothing. `tests/conftest.py:_stop()` uses the same
`urlopen` default for its shutdown call; test-only, fix for consistency. Separately, whether Claude Code's
`http` hooks honour `HTTP_PROXY` for the hook URL is **unverified** here (closed-source client); the first
work-laptop run should check it with the same local-sink method and record the result in `docs/probes/`.

#### FIX-BEFORE-M2

**F1. Any scheduled job more than 49.7 days out kills the scheduler thread, silently and persistently.**
`assistant/scheduler.py:82-84`: `delay = heap[0].ts - now; self._cond.wait(timeout=delay)` sits outside the
`try` in `_run()`. `threading.TIMEOUT_MAX` is `4294967.0` s on this interpreter (Windows); a larger timeout
raises `OverflowError`, which ends the thread. Reachable through: `POST /v1/reminders` structured form with
`at` up to `MAX_AHEAD_SECONDS` = 366 days (`routes_reminders.py:15,47`); the text grammar (`"x in 60d"`,
`grammar.py:23` allows up to 366 days) from the HTTP route **and from the Remind-me input in the overlay —
no token needed**; `POST /v1/cards` or a dropped file with `expires_at` more than 49.7 days ahead
(`model.py:177-181` accepts any finite number) via `App._arm_tick()`; and F2. Observed in-process:

```
POST /v1/reminders {"title":"far","at":now+300d}   -> 201
Scheduler().at(now + 300 days, fn)                   -> thread alive after 0.3 s: False
Scheduler().at(now + 0.2 s, fn) afterwards           -> never fires
Scheduler().at(1e308, fn)                            -> thread alive: False
```

Consequence: reminders stop firing, the `events/` file drop stops polling, card fades/snooze-returns/expiry
stop — for the rest of the process lifetime, with no `app.log` line (the exception escapes `_run()`;
`threading.excepthook` prints to stderr, which `pythonw` discards). Because `reminders.json` persists the
far reminder, `ReminderStore.start()` re-arms it on every launch and the thread dies again within one loop
iteration: the breakage survives restarts until the user hand-edits `reminders.json`. Security framing is
availability only, from a token holder or the user's own input, so not a BLOCK on this review's criteria —
but it is a product-breaking correctness bug qa's M1-6 criterion ("`x in 1m` fires") does not catch, and I
recommend tech-lead treat it as merge-blocking on correctness grounds. Fix: in `_run()`, clamp the wait
(`self._cond.wait(timeout=min(delay, 3600.0))` — the loop re-evaluates the heap head after each wake, so a
long sleep in hourly steps is behaviourally identical) and wrap the body so any exception logs and
continues. Belt-and-braces: cap `expires_at`/`timer_started_at`/`snoozed_until` at `now + 366 days` in
`model.validate_fields` and `store.snooze`, and clamp on `ReminderStore._read()`.

**F2. `POST /v1/cards/{id}/snooze` accepts `minutes: 1e308`, stores `snoozed_until = inf`, returns 500,
and leaves the list API broken until the card is dismissed.** `store.py:141-146` (`minutes <= 0` is the
only bound; `now + 1e308 * 60.0` overflows to `inf`), `routes_cards.py:130` (`JSONResponse(card.to_dict())`
raises `ValueError: Out of range float values are not JSON compliant: inf` *after* `_Guard.__exit__` has
already persisted the card). Observed in-process:

```
POST /v1/cards/<id>/snooze {"minutes": 1e308}  -> handler raised ValueError (client sees 500)
store.get(id).snoozed_until                     -> inf        store.next_deadline() -> 1e+308
GET /v1/cards  afterwards                       -> ValueError (500)      GET /v1/cards/<id> -> ValueError (500)
state.json contains the literal  Infinity       (json.dumps default allow_nan=True; stdlib reloads it)
CardStore(state.json).next_deadline()           -> 1e+308  (so the running app also hits F1 via _arm_tick)
DELETE /v1/cards/<id>                           -> 204; GET /v1/cards -> 200 again
```

Fix: bound `minutes` (e.g. `0 < minutes <= 366*24*60`) in `store.snooze()`; write state with
`json.dumps(..., allow_nan=False)` inside a try so a non-finite value can never reach `state.json`; and
keep `parse_json`'s finite check (already correct for input) — the overflow is arithmetic, not parsing.

**F3. Port already in use: the app exits with no visible signal while Claude Code hooks keep posting the
token to whoever holds the port.** `assistant/server/app.py:147-151` (`except SystemExit: log.error(...)`),
`assistant/app.py:86-89` (`log.error(...); return 1`). Observed with a plain socket bound to the configured
port first:

```
python -m assistant   -> exit 1 after 0.3 s
app.log ERROR: [Errno 10048] error while attempting to bind on address ('127.0.0.1', <port>) ...
app.log ERROR: server failed to start on 127.0.0.1:<port> (port in use?)
app.log ERROR: could not start the HTTP server on port <port>
pid file written: False   token created: True   UI shown: none
```

Under the Startup shortcut (`pythonw.exe`, `install.ps1:61-62`) the user sees nothing, and every Claude Code
tool call then delivers `Authorization: Bearer <token>` plus the hook payload (cwd, tool input, last
assistant message) to the squatting process. Exposure window measured: a squat is only effective **before**
the app binds — once uvicorn listens, a second same-user socket on `127.0.0.1:<port>` is refused with
WSAEADDRINUSE (plain, `SO_EXCLUSIVEADDRUSE`) or WSAEACCES (`SO_REUSEADDR`); a wildcard `0.0.0.0:<port>`
`SO_REUSEADDR` bind succeeds (uvicorn sets `SO_REUSEADDR`, `uvicorn/config.py:601`) but new loopback
connections still reached the app (`/v1/health` 200). A different local account cannot bind at all. So the
realistic path is a same-user process starting first at logon, or the app having died. The token is a
static bearer, so the client side cannot authenticate the server; mitigations are visibility and a pid check:
(a) on bind failure show a `MessageBoxW` (ctypes, no new dependency) naming the port and, via
`GetExtendedTcpTable`/`Get-NetTCPConnection`, the owning pid and image name, and log the same; (b) in
`send.post()` and `run_shutdown()` compare the listening socket's owning pid with `assistant.pid` before
sending the token, and refuse with a clear message on mismatch; (c) `--doctor` "port in use" should name the
owner. Also fix the `_run()` log line to say "port in use" only when `errno == 10048`.

**F4. `url`, `icon` and `actions[].id/label/shortcut` have no length cap; `title` (120) and `detail` (500)
do.** `model.py:171-175` (`isinstance(str)` only), `:199-205`. Observed: `POST /v1/cards` with a 60,000-char
`url`, a 60,000-char `icon`, and a 60,000-char action `id` each returned 201 and stored the value
verbatim; the body is inside `CARD_BODY_MAX` (65,536). The `url` is rendered as wrapped canvas text
(`cards_ui.py:166-169`), so a 60 KB URL produces a card taller than any monitor whose Dismiss button is
below the screen edge (non-sticky kinds still fade 20 s after hover; `waiting`/`meeting` are sticky and
would need the HTTP API to dismiss). `state.json` grows accordingly. Token holder only, so not a BLOCK.
Fix: cap `url` at 2,048, `icon` at 256, action `id` at 64, `label` at 40 (already truncated to 20 at
render), `shortcut` at 16, with the usual `field:` 422; cap open cards per store (e.g. 500 → 429/422 with
`code: "too_many_cards"`) since `_save()` rewrites the whole file on every change.

#### NOTE (hardening, tracked)

**N1. urllib forwards `Authorization` across redirects.** `HTTPRedirectHandler.redirect_request` copies every
header except `content-length`/`content-type`. Observed: a loopback squatter answering 302 to a second local
port made `send.post()` deliver `Authorization: Bearer <token>` to the redirect target (status 200 reported
to the caller). A squatter already holds the token (F3), so this only matters when the squatter has no
network of its own; the fix is part of B1 (redirect handler returning `None`).

**N2. `model._logged_unknown` grows without bound.** `model.py:97-100`. A 64 KB body with 3,000 distinct
unknown keys grew the set by 3,000 and wrote 3,000 WARNING lines (log growth is bounded by the 2 MiB x 4
rotation; memory is not). Fix: stop recording after, say, 50 distinct keys and log one "further unknown
fields not logged" line.

**N3. Control and bidi characters survive into titles and details.** `claude_sessions._text()` (`:32-33`)
collapses whitespace via `str.split()`, which drops `\n\r\t\v\f` and the Unicode separators but keeps C0/C1
controls (`\x00`, `\x1b`) and format characters (`\u202e` right-to-left override). Observed: a hook with
`cwd: "\u202e/evil\x00\x1b[31m"` produced a card titled `'evil\x00\x1b[31m'`. Tkinter canvas text is inert
(round-trip test: `$x`, `[exec]`, `%s`, NUL and the bidi override all came back byte-identical with no Tcl
substitution), so this is display spoofing at most (a reversed command summary), not injection. Fix:
strip `unicodedata.category(c) in ("Cc", "Cf")` in `_text()` and in `validate_fields` for `title`/`detail`.

**N4. Crash residue disables the home re-ACL check.** `paths.py:19` `_KNOWN_FILES` matches `token.tmp` and
`hooks-install.json.tmp` but not `state.json.tmp`, `state.json.corrupt`, `reminders.json.tmp`,
`reminders.json.corrupt` or `settings.json.tmp` (all written by `store._save`/`_load`, `reminders._write`/
`_read`, `settings.save`). After a crash mid-save, `secure_home()` logs "not restricting ... contains files
that are not the assistant's" on every start and never re-applies the ACL. Harmless when the ACL was applied
on first run (it persists), a gap if that first run failed. Fix: allow `\.(tmp|corrupt)$` suffixes on the
known names.

**N5. The bearer token now lives in `~/.claude/settings.json` and in `hooks-backup/*.json`.** By design
(Claude Code `http` hooks need a literal header; `hooks_installer.py:41-42`). `settings.json` carries the
profile's inherited ACL (user, SYSTEM, Administrators) rather than the token file's single ACE — the same
principals in practice. The real exposure is behavioural: that file is routinely shared, screenshotted and
committed to dotfiles repos, and `claude --debug` style output may print hook configuration. Record in the
README/hooks docs that the file contains the Assistant token and that `hooks remove` deletes it. The
backups under `hooks-backup/` contain the user's *entire* pre-install settings (possibly their own `env`
secrets) and are never pruned; keep them (they are the restore source) but `uninstall.ps1`'s deletion prompt
should mention them explicitly. Dry-run redacts correctly (`<token redacted>`, observed in tests).

**N6. Token regeneration (AC-MC-9) must re-run the hooks installer.** `token.regenerate()` has no caller
yet besides `ensure()`. When a Settings action lands (M2+), it must call `hooks_installer.install()` so the
hooks do not keep sending the revoked token (and `_is_ours` keeps matching the old entry for replacement —
it matches on URL, not token, which is the right key). Flag for the M2 review.

**N7. `uninstall.ps1` `Stop-Process` fallback does not check the process image.** `uninstall.ps1:21-25`.
Reached only when `shutdown` exits 2 (the port answered 404 to `/v1/shutdown` with a valid token — an older
Assistant build), so pid-reuse exposure is minimal: a connection failure returns 0 and a squatter without the
token returns 401 → exit 1, neither of which kills anything. Hardening: `Get-Process -Id $recorded` and
require `ProcessName -match '^pythonw?$'` before `Stop-Process`. The pid file is written only after a
successful bind (`app.py:90`) and removed on clean shutdown when the pid matches (`:228-235`); observed
`assistant.pid` = `<pid>\n<port>` with the inherited user-only ACL, gone after `/v1/shutdown`.

**N8. The repo folder is the trust root for the Startup shortcut.** `install.ps1:61-63` targets
`<python dir>\pythonw.exe -m assistant` with `WorkingDirectory=$repo`, so whatever `assistant/` package sits
in that folder runs at every logon. Same as any user-installed Python tool; mention in the README that the
folder should not be world-writable or on a shared drive. No elevation, `--user --only-binary :all:`
(`:33`), `--init` not `--doctor` for first-run creation (N7 of Review 1 is closed), prompts before writing
hooks (`:44-51`), nothing downloaded or executed from a remote location — all confirmed.

**N9. `pillow==13.0.0` is installed in the dev venv but is neither in `requirements.txt` nor imported.**
`pip list` vs `requirements.txt`: the 29 pins match exactly (no mismatches, nothing missing); `pillow` is the
only non-dev extra and `grep -rn "PIL\|pillow" assistant` finds nothing. Plan section 10.1 lists pillow for
M1 but M1 did not need it. Not a security issue; either `pip uninstall pillow` in the venv or add it when it
is actually used. `pywin32` remains the only compiled dependency we introduce. Hash-pinning (Review 1 N8) is
still open.

**N10. Hardlinks bypass the file-drop symlink check.** `filedrop.py:65` skips `is_symlink()` and
non-files; a hardlink (`mklink /H`) to a file elsewhere was read and processed (rejected here for having no
`title`; it would have become a card if it were a valid card body) and the link name was moved into
`rejected/`, leaving the original path intact. Creating the hardlink required write access to the target,
and `events/` is user-only (`(I)(OI)(CI)(F)` observed), so the boundary is unchanged; recording for the
threat model. A symlink could not be created in this session (no SeCreateSymbolicLinkPrivilege), so the
`is_symlink()` branch is **unverified by observation**; the junction (`mklink /J ... junc.json`) and a
directory named `dir.json` were both skipped as expected.

**N11. Hook payload content is shown on screen and persisted, never logged.** `_tool_summary()` puts the
first of `command`/`file_path`/`path`/`url`/... into the card detail (observed: a `curl -H 'Authorization:
Bearer SECRET123'` command appeared in the `waiting` card detail and in `state.json`, and in neither
`app.log` nor the console). This is the reference app's intended behaviour and SEC-3 does not cover cards;
noting it because the M2 "permission card" design may want to mask obvious bearer/`-H Authorization`
fragments in the summary.

**N12. Open items carried forward unchanged:** R2-6 (occasional connection reset instead of 413 on
oversize declared bodies — not re-measured, the single 2 MB probe got a clean 413), R2-9 (FAT/exFAT home
unverified), R2-10 (`ws_max_size` for M3b), R2-11 (per-file ACL on `settings.json` when secrets land, M2),
Review 1 N6 (token never in a URL, M3b) and N8 (hash-pinned requirements).

### What was checked and found sound (PASS checklist)

- **SEC-11, hook receiver is passive.** Ten payload shapes including decision-shaped ones
  (`decision: allow`, `hookSpecificOutput.decision.behavior`, `permissionDecision`, `continue: false`,
  `additionalContext`, `systemMessage`), an unrecognised event, `StopFailure`, `SessionEnd` and a body with
  no `hook_event_name` all returned exactly `200 {}`. Nothing in `routes_hooks.py` or `claude_sessions.py`
  reads the response side; `handle()` exceptions are logged and still answer `{}` (`routes_hooks.py:16-20`).
  qa's `test_response_never_contains_a_decision_key` covers the word list. The 400 bodies for non-object
  payloads carry only `{"error": {...}}` (no decision key).
- **Malformed / huge / nested hook bodies (observed, in-process):** `{not json` 400, `[1,2,3]` 400, `"x"`
  400, `null` 400, `NaN`/`Infinity`/`1e999` 400 (strict `parse_json`, `routes_cards.py:54-56`), invalid
  UTF-8 400, UTF-8 BOM accepted, `[` x 100,000 and `{"a":` x 50,000 → 400 (`RecursionError` caught,
  `:79`), empty and whitespace bodies → `{}` → 200, 1 MiB + 1 → 413. No 500 on any input.
- **Host / Origin / bearer on every new route (observed, live instance):** `/v1/shutdown` POST no token
  401, bad `Host` 403, bad `Origin` 403, GET with token 405 (method check after auth); `/v1/hooks/claude-code`
  401 / 403 / `Origin: null` 403 / valid 200; `/v1/cards` 401, `Origin: http://localhost.evil` 403,
  `Origin: http://localhost:3000` 201; `/v1/reminders` 401; `OPTIONS /v1/cards` 401; 2 MB declared body
  413 before any route. Order Host → Origin → bearer → body cap unchanged (`auth.py:50-58`,
  `server/app.py:97-98`). Response headers on 201: `content-length, content-type, date, server` only (no
  CORS headers). Routes appended in `App.run()` (`app.py:81-84`) go into the same router, so the middleware
  covers them — confirmed by the 401/403 results above.
- **`/v1/_debug/ui` gating (observed):** without `ASSISTANT_TEST_MODE`, GET with a valid token → `404 Not
  Found` (the `Route` is never constructed, `app.py:82-84`), without token → 401. With `=1`: 401 without
  token, 403 with bad Host, 200 with token; `app.log` carries `WARNING ASSISTANT_TEST_MODE=1: serving
  /v1/_debug/ui`. Payload keys: `cards[] {id, kind, colour, title, priority, rect, hidden, target_rect,
  monitor, hwnd, seen, blinking, timer, buttons, exstyle_flags}`, `icon {hwnd, rect, exstyle, exstyle_flags,
  count, muted, body_colour, scale}`, `menu`, `mute_choices`, `sound_on`, `reminder_input_open`, `strips`.
  Card `detail` and `url` are **not** in the payload; the token is not. Window handles are harmless to a
  local token holder.
- **`/v1/shutdown` (observed):** 202 `{"status":"shutting down"}`; process exit code 0 within the 15 s
  wait; `assistant.pid` removed; `app.log` shows `shutdown requested over HTTP` → `shutting down` →
  uvicorn `Finished server process`. Any token holder can stop the app — by design (the token is the user).
- **Card `url` opened on click (observed via `App._open_url` with `webbrowser.open` stubbed):** opened —
  `https://ok.example/x`, `HTTP://UPPER.example`, `http://a\nb`, `https://evil.example\@good.example`,
  `http://127.0.0.1:17171/v1/shutdown` (a GET; the route is POST-only and needs the bearer, so inert),
  `https://x.example/#javascript:1`; refused — leading space, `javascript:`, `file:///C:/Windows/win.ini`,
  UNC `\\server\share\x`, `http:\\backslashes`, fullwidth-colon `http：//`, `ftp:`, `data:`, `ms-settings:`,
  `hxxp:`. On Windows `webbrowser.open` ends in `os.startfile(url)` or a `[browser, url]` argv list — no
  shell, so the accepted http(s) strings reach only the registered browser. Title/detail rendering is
  tkinter canvas text with no markup language (round-trip test above); `actions[].id` is used only as a
  dictionary key and event payload (`store.press`, `:167-175`), `label` is truncated to 20 characters at
  render, `icon` is not rendered in M1.
- **File drop trust model (observed with `FileDrop.poll()` on a scratch `events/`):** 70 KB file →
  `rejected/` with `File is larger than 65536 bytes.`; `{nope` and `[` x 50,000 → `The file is not valid
  JSON.`; a card with an invalid `kind` and a `password` field → reason names the field only, the value
  (`hunter2`) appears in no `.error.txt` and no log line; `UPPER.JSON` processed (case-insensitive);
  `..json` processed; a directory `dir.json` and a junction `junc.json` skipped; `notjson.txt` ignored; a
  file written within the 0.25 s settle window deferred (`made=0, busy=True`) and consumed 0.3 s later;
  two more `bad.json` drops after the first produced `bad.<ms>.json` siblings, no overwrite. File names
  come from `os.scandir()` of `events/` itself, so they cannot contain separators; `rejected/` and its
  `.error.txt` files inherit the user-only ACL. Consumed files are deleted, undeletable ones are remembered

### New findings, ranked (all NOTE)

**R4-1. With no `assistant.pid`, the CLI still hands the token to whatever listens on the port.**
`send.py:46`: the mismatch check needs both a recorded pid and a listener pid. The pid file is removed on every
clean shutdown (`app.py:265-272`) and does not exist before the first run, so in those states a same-user
process holding the port receives the bearer token from `send`/`shutdown`. Observed: pid file deleted,
squatter listening → `send` exit 0 printing the squatter's answer (`sink`), squatter received `POST /v1/cards`
with `Authorization`; `shutdown` → "shutdown requested", second request delivered. Severity NOTE, not BLOCK:
the squatter must already run as the user, and Claude Code's `http` hooks deliver the same token to it
regardless of the CLI (Review 3 F3) — the CLI check reduces exposure only in the crash-residue case, which it
now does. Hardening: when there is no pid file, refuse unless `netinfo.process_image(listener)` is a
`python`/`pythonw` image (message: "no assistant.pid; port is held by <image>"), or simply refuse with
"Assistant is not running (no assistant.pid)". Test exists for the current behaviour
(`test_cli_sends_when_the_listener_pid_matches_the_pid_file` relies on a pid-file match, so a stricter rule
would not break it).

**R4-2. A stale pid file whose pid was reused by any python process makes the Assistant refuse to start —
with the port free.** `app.py:117-130` `_another_instance_running()` treats "pid alive and image starts with
`python`" as "Assistant running" and never consults the port. Observed: fresh home, port free
(`listener_pid(port) is None`), `assistant.pid` = pid of an unrelated `python.exe -c "time.sleep(600)"` →
`python -m assistant` exit 1, `Assistant is already running (pid <n>). This second copy will exit.`, pid file
left in place; after that python process exited the Assistant started normally. Under the Startup shortcut
this is a `MessageBoxW` at logon and no overlay, hooks posting into a closed port, and no self-heal until the
foreign process exits or the user finds and deletes `assistant.pid` (the message does not name it). Needs a
prior crash/kill (clean shutdown removes the file) plus pid reuse by a python process — plausible on a
developer laptop. Availability only, no attacker, so NOTE; recommended for the next dev pass because the fix is
small: also require `netinfo.listener_pid(recorded_port) == pid`, where `recorded_port` is the second line of
the pid file (not `settings.port`, so a running instance on a previously configured port is still detected);
when the pid is alive but not listening there, treat the file as stale, log it, and proceed to bind. Name the
pid-file path in the refusal message.

**R4-3. asyncio proactor `ConnectionResetError` tracebacks in `app.log` (qa's follow-up).** Mechanism confirmed
in the interpreter's stdlib (`C:\Python313\Lib\asyncio\proactor_events.py:154-167`, 3.13.1):
`_call_connection_lost()` calls `self._sock.shutdown(socket.SHUT_RDWR)` unguarded inside `finally`; when the
peer has already reset the connection this raises, the loop's `call_exception_handler` logs `Exception in
callback ..._call_connection_lost` with a traceback at ERROR on the `asyncio` logger (root handlers →
`app.log`), and — because the exception leaves the `finally` early — `self._sock.close()` and the server detach
are skipped, so the socket handle lives until the transport is garbage-collected (`__del__` warns and closes).
Triggerable by any local process that can connect to `127.0.0.1:<port>`; no token needed, because it happens at
the transport layer before auth. Not reproduced here: 40 requests (half authenticated) RST'd with `SO_LINGER
0` immediately after the request bytes produced 0 tracebacks, app healthy — the fast routes had already
written their response; qa saw it ~1 in 20 on `/v1/_debug/ui`, whose response waits on the UI thread. Impact:
log noise bounded by the 2 MiB x 4 rotation, buries real errors, slow handle leak under a deliberate flood.
NOTE. Fix: a `logging.Filter` on the `asyncio` logger dropping records whose `exc_info[0]` is
`ConnectionResetError` and whose message contains `_call_connection_lost` (keep everything else), installed in
`_setup_logging()`; the handle leak is CPython's and goes away with the same reset being swallowed upstream
only, so note it in the threat model rather than patching stdlib.

**R4-4. `uibus.submit()` guard is check-then-act.** `uibus.py:32-37`: `if not future.done():
future.set_exception(exc)` / `set_result(result)` — a `cancel()` from the asyncio thread (`asyncio.wait_for`
timeout in `_debug_route`, `app.py:253`) landing between the `done()` check and the set raises
`InvalidStateError` inside `run()`, which `drain()` logs as `uibus callable failed` with a traceback. Window is
a few instructions; not demonstrated (qa's 20-thread hammer test passed). Hardening: wrap the two set calls in
`try/except concurrent.futures.InvalidStateError: pass`. NOTE.
